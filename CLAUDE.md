# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The public website for ACBB Canoë-Kayak et SUP (a canoe-kayak/SUP sports club in Sèvres, France), built with [Pelican](https://getpelican.com/) (static site generator) using a custom theme (`themes/acbb`) reconstructed from an export of the club's real WordPress site (Bridge/WPBakery theme).

## Commands

```bash
source .venv/bin/activate                          # or prefix commands with `uv run`

pelican content -o output -s pelicanconf.py         # build the site (dev config)
pelican content -o output -s publishconf.py         # build with production SITEURL/feeds
rm -rf output && pelican content -o output -s pelicanconf.py   # clean rebuild

cd output && python3 -m http.server 8123            # serve output/ locally for manual checks
```

There is no test suite, linter, or CI configured. Verify changes by rebuilding and checking the rendered HTML/CSS in a browser — there's no other feedback loop.

Dependencies are managed with `uv` (`uv add <pkg>` — updates `pyproject.toml` and `uv.lock`, and reinstalls `acbb_kayak_sup` in editable mode).

## Architecture

### Content is Markdown, presentation is HTML — strictly separated

**Site content lives in `content/**/*.md`, all markup lives in `themes/acbb/templates/`.** There is no YAML content and no custom reader — Pelican's built-in `MarkdownReader` handles everything. A content file has standard Pelican `Key: value` metadata at the top (`Title`, `Slug`, `Status`, `Summary`, and for the homepage `Save_as`/`Template`/`Image`), a blank line, then the Markdown body:

```markdown
Title: Pourquoi nous choisir ?
Slug: pourquoi-choisir-acbb
Status: published
Summary: ...

## Plus qu'un sport, une énergie partagée.

Regular paragraph text with **bold** and [links](url).
```

**Prose uses real Markdown syntax** (`##`/`###` headings, `**bold**`, `*em*`, `[text](url)`, `![alt](src)`, `- ` lists). **Layout is written as semantic HTML5 directly in the `.md` file**: every top-level block is a `<section>` or, for a repeatable self-contained item, an `<article>` — these are what get the page's "reading column" treatment (centered, `max-width:900px`) by default. A `.split`/`.split-narrow` modifier class turns one into a two-column CSS Grid row (even split, or narrow-image/wide-text) instead — this replaced WPBakery's `vc_row`/`wpb_column`/`vc_col-sm-N` div-grid system entirely (theme rebuilt away from it; see git history for the old markup if you need it). Other reusable per-block classes: `.cta-dark` (full-bleed dark CTA band, its direct children individually recentered to the reading column), `.activity-card` (image+text+button card, combine with `.split-narrow`), `.faq` (wraps `<details>/<summary>` FAQ items), `.pricing` (wraps `<table class="price-table">` groups), `.social-links` (wraps a `<nav><ul>` of icon links), `.simple_gallery` (static grid, used on marketing pages only), `.article_carousel` (auto-advancing horizontal photo carousel with a fullscreen lightbox on click, used in `content/blog/*.md` instead of `.simple_gallery` - see "Blog articles" below), `.instagram_grid`, `.map_embed`. Falling back to raw HTML for anything Markdown has no syntax for is itself standard Markdown practice (CommonMark says so explicitly) — this isn't a workaround, it's how the format is meant to be used. `page.html`/`article.html`/`home.html` just render `{{ page.content }}` inside `<main>` — there is no template-side block dispatch system (an earlier YAML-block prototype was removed; see git history if you need to look at it).

**`md_in_html` lets Markdown syntax work *inside* a raw HTML wrapper**, via `markdown="1"` on the wrapping tag (enabled in `pelicanconf.py`'s `MARKDOWN` setting, along with `markdown.extensions.extra`). This is what lets `**bold**`/`[links](url)`/`##`-headings be used inside `<section markdown="1">` instead of hand-typing `<strong>`/`<a>`/`<h2>`.

**The hard-won gotcha, worth reading before touching any `.md` file:** `md_in_html` only recognizes a `markdown="1"` block correctly if **every single ancestor tag of that element, all the way up to the top of the raw-HTML block, is on its own line** — one opening tag per line, no exceptions. If *any* ancestor line has two or more tags on it, `md_in_html` silently fails for everything nested inside — the Markdown syntax (`##`, `**bold**`) leaks into the output as literal unprocessed text instead of being converted to HTML. This is *not* about the `markdown="1"` element's own immediate parent line; a multi-tag line several levels further up the tree still breaks it. Concretely:
- A **top-level, standalone** `<section markdown="1">` (not nested inside a `.split`/`.split-narrow` grid or an `.activity-card`) is always safe — this is the common case, used throughout for centered heading+paragraph+button sections.
- Inside a **`.split`/`.split-narrow` row or an `.activity-card`**, do **not** use `markdown="1"` — write plain HTML with hand-typed `<strong>`/`<em>`/`<a>`/`<h3>` tags instead. Every existing multi-column/activity-card region in this codebase does this; that's not a stylistic choice, it's required for correctness. If you're tempted to add `markdown="1"` inside one of these, either restructure so the tag-per-line convention holds all the way to the root, or (simpler, and the established pattern here) just write the inline tags by hand.
- If output ever shows a literal `##` or `**` instead of a rendered heading/bold text, this is almost certainly the cause — check `grep -rn 'markdown="1"'` in the offending file and verify every ancestor line above it has exactly one tag.

**Heading-level gotcha:** the Bridge stylesheet's WP-Customizer-generated CSS sets `h4 { color: #ffffff; font-size: 24px; }` **globally**, on the assumption h4 is only ever used in dark-background contexts (e.g. footer widget titles) — it is not scoped to those contexts. Using `<h4>` for an ordinary heading on a white background renders it invisible (white-on-white). Use `<h3>` for column/card headings instead (the convention used throughout: `<h3><strong>Un club pour tous les niveaux</strong></h3>`, etc.) — `<h4>` is only safe when you also set its color explicitly (e.g. the homepage's `#### Sur Instagram @acbbcanoe { style="color:#ef7f01;" }`, matching the original page's own inline color override on that specific heading) or when it's genuinely inside a dark/`.cta_dark` context.

**Attribute-list heading gotcha:** to attach an inline style/class to a Markdown heading (`markdown.extensions.attr_list`, included via `extra`), the `{: ... }` syntax must be **on the same line as the heading**, e.g. `#### Heading { style="color:#ef7f01;" }` — putting it on the line below (which *does* work for paragraphs, e.g. a `**bold**` paragraph followed by `{: style="..." }` on its own line) produces a stray literal `{: ... }` paragraph and leaves the heading unstyled. In practice, prefer a `.cta_dark`-style CSS class on the wrapping `<div>` over per-element `attr_list` styling wherever the whole block needs one color (simpler, no risk of the above), and use inline `style="color:..."` on a hand-written `<h4>`/`<span>` only for genuine one-offs like the Instagram heading.

**Gotcha:** keep block markup exactly matching the CSS class names in `theme.css` (`.split`, `.split-narrow`, `.cta-dark`, `.activity-card`, `.faq`, `.pricing`, `.wide`, ...), since there's no schema validation catching typos now.

### Theme (`themes/acbb`)

- `templates/base.html` — page shell: `<header class="site-header">` (logo + Pelican-`pages`-driven `<nav class="site-nav">`, one shared `<ul>` for desktop and the mobile off-canvas toggle, not three separate duplicate lists), `<main class="site-main">` (hero block + `{% block content %}`), `<footer class="site-footer">` (hardcoded club address/transit info — genuine, non-changing club data, not settings-driven), and the `theme.js` script include.
- `templates/index.html`, `article.html`, `page.html`, `home.html`, plus the full fallback set (`archives`, `category`, `tag`, `author`, `categories`, `tags`, `authors`, `period_archives`) so Pelican never hits a missing-template error regardless of what content exists. `page.html`/`article.html` inject the page/article `<h1>` via a plain `<header class="page-header">`, not a multi-level div grid.
- `static/css/bridge-*.css` — copied verbatim from the original WordPress export (Bridge theme reset/typography/colors/`.qbutton`/print styles). Don't hand-edit these; layer fixes in `theme.css` instead. `vc-grid.css` (WPBakery's row/column grid CSS) was dropped entirely — nothing in the current markup uses `vc_row`/`wpb_column`/`vc_col-sm-N` classes anymore.
- `static/css/theme.css` — all theme-specific styling: header/nav/footer chrome, and the content-area layout system (`.split`/`.split-narrow`/`.wide` modifiers on a `<section>`/`<article>`, `.cta-dark`, `.activity-card`, `.faq`, `.pricing`, `.social-links`, `.simple_gallery`, `.article_carousel`/`.lightbox`, `.instagram_grid`, `.map_embed`). Each rule has a comment explaining which upstream WordPress/JS behavior (or, post-rebuild, which earlier div-grid convention) it's replacing. Notable ones:
  - `.site-header { position: sticky; top: 0; }` — replaces the original's JS scroll-position-computed fixed header (`bridge-default.js`'s `headerSize()`) with a plain CSS sticky header; always visible on scroll rather than hide-on-scroll-down, since this build's header is already forced opaque (no transparent-over-hero state to preserve).
  - `.site-main > :is(section, article)` gets the centered `max-width:900px` "reading column" treatment by default; the `.split`/`.split-narrow` combo widens to `1200px` and switches to a 2-column CSS Grid, `.wide` just widens without going 2-column (e.g. the homepage's article-teaser section: centered heading, full-width card grid below). **Specificity gotcha:** any override of this base rule (e.g. `.faq`/`.pricing`'s `text-align:left`) must match or exceed its specificity (`.site-main > :is(section, article)` = one class + one type twice) — a bare `.faq {text-align:left}` silently loses regardless of source order. Repeat the `.site-main > :is(section, article)` prefix on the override selector rather than relying on cascade order.
  - `.cta-dark { max-width: none !important; } .cta-dark > * { max-width:900px; margin:auto; }` — the row itself stays full-bleed for the background color while each direct child (not a nested wrapper div) is individually centered to the reading column — reproduces WPBakery's "full-width row, narrow column" look without the nested div.
  - `.page-header h1 { text-transform: uppercase; }` — the auto-injected top-of-page `<h1>` reproduces the original's convention of hand-typing page headings in full caps in the page body, independent of the actual (mixed-case) WP post title used for `<title>`/breadcrumbs. This is CSS-only so `page.title`/`<title>` stay normally cased. It does **not** generalize to other headings: in-body `h2`/`h3` headings follow the original's actual per-heading capitalization, which is inconsistent by hand-authoring (e.g. homepage's "Plus qu'un sport..." is mixed-case, "TOUTES LES ACTIVITÉS" is caps) — when adding a heading, check the live page's actual text rather than assuming a rule.
  - `body{font-family:'Roboto'}` — the live site's Google Fonts request loads *both* Raleway and Roboto, but computed styles on the live site confirm Roboto is what's actually applied everywhere (body, headings, nav); Raleway is an unused theme-default leftover. Don't reintroduce Raleway based on the font list in a page's `<head>` alone — check computed style on the live site if in doubt.
- `static/js/theme.js` — the only JS this site ships: mobile nav toggle (`.nav-toggle` button ↔ `aria-expanded` + `.is-open` on `#site-nav`) and back-to-top button show/hide + smooth scroll. No jQuery, no jQuery Migrate, no Modernizr, no Bridge JS bundle — all of that (`bridge-default.js`/`bridge-default-dynamic.js`, header/menu/scroll behavior) was dropped along with the div-grid markup it depended on, in favor of this ~30-line vanilla script plus plain CSS (`position:sticky` for the header). Confirmed via grep before dropping that nothing else on the site depends on jQuery being global or on Modernizr's `html.js`/`html.no-js` classes (the only CSS keyed to those is for the owl-slider/portfolio carousel, unused here). Everything else WordPress-plugin-specific from the original export (WPBakery composer runtime, Contact Form 7, Instagram feed, jQuery UI widgets, MediaElement, prettyPhoto, flexslider, isotope, skrollr, ...) was already dropped earlier for the same reason: dead weight/broken without a live WP backend or the page-builder editor.
- `static/images/` — logo (`logo.png` + `logo-mobile.png`, both required: the header's `<picture><source media="(max-width:1000px)">` swaps to the mobile logo below the nav breakpoint), hero default background, footer transit icons, map. Only images actually referenced by templates — don't bulk-copy from a WordPress export again.

### Page titles vs. menu titles

A page's `Title:` is what shows in its own `<h1>`/`<title>`/breadcrumbs and never changes for nav purposes. An optional `MenuTitle:` metadata field overrides *only* what's displayed for that page in the header nav, its "Les activités" submenu entry (if hidden), and the footer's "Plus de liens" list — useful when the real title is too long for a menu item (e.g. `inscription.md`'s `Title: Inscriptions 2026-2027` / `MenuTitle: Inscriptions`, `pourquoi-choisir-acbb.md`'s `Title: Pourquoi choisir l'ACBB ?` / `MenuTitle: Nous choisir`). All three nav loops in `base.html` render `{{ p.menutitle or p.title }}` (Jinja's `or` treats a missing/undefined metadata field as falsy, so pages without `MenuTitle:` just fall through to `Title:` as before). Don't add fallback logic anywhere else — `article_list.html`/blog cards and any other place a title is shown as *content* rather than *navigation* should keep using `.title` directly.

### Homepage

`content/pages/accueil.md` sets `Save_as: index.html` (written to the site root instead of `pages/accueil.html`) and `Template: home` (a standard Pelican metadata key) to use `templates/home.html` instead of `page.html` — that skips `page.html`'s auto-injected `<h1>{{ page.title }}</h1>` (the homepage's first section supplies its own heading, matching the original site's `qode-title-hidden` behavior) and uses a taller hero. Because the homepage owns `index.html`, the article-listing index was moved to `/blog/` via `INDEX_SAVE_AS = "blog/index.html"` in `pelicanconf.py`. `base.html`'s nav/footer loops over `pages` all filter `if p.save_as != 'index.html'` to avoid listing the homepage a second time next to the hardcoded "ACCUEIL" link.

`home.html` also appends a "Paroles d'adhérents" (latest articles) section directly in the template, *after* `{{ page.content }}`, guarded by `{% if articles %}` — real Pelican articles can't be authored inside `accueil.md` itself, so this is template logic, not Markdown content. It reuses `templates/article_list.html` (`{% set article_list = articles[:3] %}`).

### Blog articles (`content/blog/`) and Actualités (`content/actualites/`)

Articles live in **two independent streams** that share the same Pelican `Article` machinery but are never mixed together: `content/blog/` (`Category: Sorties`, the original blog, converted from the live site) and `content/actualites/` (`Category: Actualités`, a news/announcements section - shorter, no-frills posts like "une séance d'essai" gratuite). Both get their own index, own nav item, and own `/*/<year>/<month>/` archive tree; see "Actualités / per-category archives" below for how that separation is implemented.

The 49 posts from the live site's `/blog/` (WordPress category "sorties") were converted into `content/blog/*.md`, one file per post, `Slug:` matching the original WP slug. `pelicanconf.py` sets `ARTICLE_URL`/`ARTICLE_SAVE_AS = "{path}/{slug}.html"` (`{path}` resolves to the article's source subdirectory - `blog` or `actualites` - via `PATH_METADATA`, see below) so each stream lands under its own URL prefix instead of Pelican's default of the site root. Every blog article carries `Category: Sorties` (the only WP category in use) and an `Image:` pointing at its downloaded featured image, both used by `article_list.html`'s cards.

**How they were produced**, for reference if more posts get added later: WordPress's REST API (`/wp-json/wp/v2/posts`) returns the post list/dates/slugs/excerpts fine, but its `content.rendered` field for WPBakery-authored posts contains *unprocessed* `[vc_row ...]` shortcode text (a plugin/REST quirk, not something fixable from this repo) — so the actual body had to come from fetching each post's live, fully-rendered permalink HTML and parsing `article .post_text_inner` instead. That markup varies a lot by era (WPBakery `vc_row`/`wpb_gallery` rows for newer posts, bare Gutenberg `<div>`s + `figure.wp-block-gallery` for older ones) but reduces to the same shape everywhere: a linear sequence of heading/paragraph/list blocks interrupted by photo galleries. Each gallery's images were downloaded into `content/images/blog/<slug>/` and rewritten as a `<section class="wide"><div class="article_carousel">` block (an auto-advancing horizontal carousel - see `.article_carousel` in `theme.css`/`theme.js`, distinct from the static `.simple_gallery` grid used on marketing pages); everything else became a `<section markdown="1">` of plain Markdown (paragraphs, `### **heading**`, `- list`), matching this repo's usual content conventions. The one-off conversion script isn't checked into the repo (it was a throwaway migration tool, not something the site depends on going forward) — a similar fetch-and-walk-the-DOM approach would need to be redone for any future bulk import.

**Gotcha carried over from the fix above:** like every other page-image reference in this repo, `Image:` metadata must be root-relative with a **leading slash** (`Image: /images/blog/<slug>/<file>.jpg`) — `accueil.md` got away with omitting it only because `index.html` happens to sit at the site root, but `/blog/<slug>.html` is one level deep, so a slash-less path resolves to the wrong directory there. Double-check this if adding a new article or page image by hand.

**Blog sidebar** (`index.html`'s `.blog-sidebar`, next to the article grid): "Articles récents" lists articles from the last 6 months, and "Archives" lists every year/month that has articles, each linking to a real Pelican period-archive page. Both are computed by helpers in `pelicanconf.py`, not hardcoded:
- `RECENT_ARTICLES_SINCE` (a `JINJA_GLOBALS` entry) is `datetime.now() - 182 days`, computed once at build time — like the rest of this static site, "recent" reflects whenever it was last built, not the visitor's actual "now". Re-running `pelican content ...` refreshes it.
- `archive_groups`/`month_name` (`JINJA_FILTERS`) group articles by year → month for the sidebar, and translate Pelican's English `calendar.month_name` into French for both the sidebar and `period_archives.html`'s page titles.
- The month/year archive pages themselves need per-category archive generation (see below) — without it there's nothing for the sidebar's Archives links to point to, so they'd 404. **Gotcha:** `themes/acbb/templates/period_archives.html` must read `period_num` (a `(year,)` or `(year, month)` tuple passed to this template) rather than `month`/`year` as separate top-level variables — those don't exist in this Pelican version's context; templates written against them silently render blank/wrong titles instead of erroring.

### Actualités / per-category archives (`plugins/category_period_archives.py`)

Once a second article stream (Actualités) existed alongside the blog, Pelican's own period-archive machinery (`YEAR_ARCHIVE_SAVE_AS`/`MONTH_ARCHIVE_SAVE_AS`) stopped being usable: those settings group **all** articles by date regardless of category, so a single `blog/2026/08/` page would silently start including Actualités posts too (and vice versa). Pelican has no built-in notion of a per-category period archive, so `pelicanconf.py` leaves those two settings unset and instead defines:

```python
CATEGORY_ARCHIVES = {"Sorties": "blog", "Actualités": "actualites"}
PLUGIN_PATHS = ["plugins"]
PLUGINS = ["category_period_archives"]
```

`plugins/category_period_archives.py` is a small local Pelican plugin (hooked in via the `get_generators` signal, the standard extension point for adding a whole new generator - see Pelican's plugin docs) that, once all the built-in generators have populated the shared Jinja context, filters `articles` down to each `CATEGORY_ARCHIVES` entry and writes its own `<prefix>/<year>/index.html` and `<prefix>/<year>/<month>/index.html` pages, reusing the theme's existing `period_archives.html` template - so the template itself doesn't know or care that this is now plugin-driven rather than Pelican-native. Both the blog's `/blog/YYYY/MM/` and the news section's `/actualites/YYYY/MM/` archive trees are generated this way now, symmetrically - not just the new section - since the moment there were two categories, the blog's own archives would otherwise have quietly started including Actualités posts too.

Two other pieces make the two streams behave as independent sections rather than one blog with a second category tag:
- **`PATH_METADATA = r"(?P<path>blog|actualites)/.*"`** (`pelicanconf.py`) makes Pelican's `{path}` URL-format field resolve to just the source subdirectory (`blog` or `actualites`) instead of its default of the *full* relative file path (dir + filename) - which is what lets `ARTICLE_URL = "{path}/{slug}.html"` give each stream its own URL prefix from one shared setting. **Gotcha:** `PATH_METADATA` is applied by Pelican to *every* file it reads, including `STATIC_PATHS` content (`content/images/`, `content/files/`) - an earlier, broader version of this regex (matching any top-level directory) silently collapsed every static asset's output path down to `output/images`/`output/files` as bare *files* (each new asset overwriting the last), because `STATIC_SAVE_AS`'s default format also uses `{path}`. The regex is deliberately scoped to only match `blog/...`/`actualites/...` source paths so it can't touch anything under `images/`/`files/`/`pages/`.
- **The Actualités index** (`themes/acbb/templates/actualites.html`, filtering the shared `articles`/`dates` context via the `by_category` `JINJA_FILTER` from `pelicanconf.py`) is generated the same way the blog index is: as a `DIRECT_TEMPLATES` entry (`ACTUALITES_SAVE_AS = "actualites/index.html"`), not a Pelican Page - real Pelican articles can't be listed from inside a Page's Markdown body. Its sidebar shows "Actus du mois" (articles whose `date.year`/`date.month` match `build_now`, a `JINJA_GLOBALS` entry computed once at build time, same "frozen at last build" caveat as `RECENT_ARTICLES_SINCE`) instead of the blog's rolling 6-month "Articles récents" window, per how this section was scoped when it was added.
- **`base.html`'s nav/footer** only render the "Actualités" link when `articles|by_category("Actualités")` is non-empty (same guard style as the pre-existing `{% if articles %}` around "Blog") - so the link doesn't appear (and 404) before any Actualités post exists.

### Content images vs. theme images

Site chrome images (logo, hero bg, footer icons) live in `themes/acbb/static/images/`, referenced from templates as `{{ SITEURL }}/theme/images/...`. Content-specific images live in `content/images/<page-slug>/` (`STATIC_PATHS = ["images", "files"]` in `pelicanconf.py` copies `content/images/` to `output/images/` and `content/files/` to `output/files/`).

**Content links/images use Pelican's `{static}`/`{filename}` intra-site link syntax, not hardcoded paths** — e.g. `<img src="{static}/images/pourquoi-choisir/dejeuner.jpg">`, `<a href="{static}/files/calendrier-sessions-2026-2027.pdf">`, `<a href="{filename}/pages/kayak-jeunes.md">`. Pelican rewrites these to the correct fully-qualified URL (respecting `SITEURL`) as a post-process regex over the *rendered* HTML output — it scans `href`/`src`/etc. attributes for the `{tag}` pattern regardless of whether the tag came from Markdown syntax or hand-written raw HTML, so this works the same inside a `<section markdown="1">` block as inside plain HTML. This is what makes the site deployable at a subpath (e.g. a GitHub Pages project site) as well as a domain root — `SITEURL=""` (dev) and any other `SITEURL` (e.g. `publishconf.py`) both resolve correctly from the same content, unlike the hardcoded-absolute-path convention this repo used earlier (see git history around the "SITEURL-templated" commit if you need the reasoning/migration).

- `{static}/...` — any file under `STATIC_PATHS` (`content/images/`, `content/files/`). Path is written relative to the content root with a leading slash, same shape as the old hardcoded path just with the `{static}` prefix added.
- `{filename}/...` — links to another page/article, written as the path to its *source* `.md` file relative to the content root (e.g. `{filename}/pages/kayak-jeunes.md`, `{filename}/articles/vogalonga-2026-grazie-venezia.md`), **not** the slug or the generated `.html` filename — those can differ (e.g. `content/pages/inscriptions.md` has `Slug: inscription`, so the correct link is `{filename}/pages/inscriptions.md`, not `.../inscription.md`). Get this wrong and Pelican logs `Unable to find '...', skipping url replacement` at build time and leaves the literal `{filename}/...` string in the output — always rebuild and grep the build log for "Unable to find" after adding a new internal link.
- Images that are genuinely theme-owned (e.g. the footer transit icons `themes/acbb/static/images/M9.png` etc.) can't be reached via `{static}` if referenced from content, since `{static}` only resolves paths under the content root — `infos-pratiques.md` needed those specific 4 icons, so they're duplicated into `content/images/icons/` rather than reached across into theme territory.
- The `Image:` page/article metadata field (used for the hero background and blog card thumbnails) is **not** covered by this substitution — Pelican only auto-rewrites `FORMATTED_FIELDS` (`summary` by default), not arbitrary metadata. Keep writing it as a root-relative content path (`Image: /images/accueil/hero.jpg`) and rely on the templates (`page.html`/`article.html`/`home.html`'s hero `<div>`, `article_list.html`'s card `<img>`) prepending `{{ SITEURL }}` themselves — that's already wired up, don't remove it when touching those templates.

### Linking to pages that don't exist yet

When content references another club page/activity that hasn't been converted to Pelican yet, link out to the real, currently-live page on `https://www.acbb-canoe-kayak.fr` instead of a stub or dead link (e.g. individual activity pages like `/kayak-jeunes/` — genuine, currently-useful destinations, not something to fake). Once a page is actually ported into `content/pages/*.md`, go back and swap the external links that pointed to it for internal `{filename}/pages/<actual-source-filename>.md` ones (see "Content images vs. theme images" above for why it's `{filename}` and not a hardcoded path now — this was done for `activites.md`, `nous-choisir.md`, `inscriptions.md`, `infos-pratiques.md`, and the 6 individual activity pages below once each existed) — don't do this speculatively ahead of the page actually existing.

### Individual activity pages (`content/pages/kayak-*.md`, `stand-up-paddle.md`)

The 6 per-activity pages (Kayak Jeunes, Kayak Loisir mer/rivière calme, Kayak Rivière, Kayak Compétition, Kayak Polo, Stand Up Paddle) were converted from the live site the same way as the other WPBakery pages (fetch the rendered permalink, walk `.wpb-content-wrapper` in document order - see the blog-article conversion note above for the general approach). They all share one structure: a left-aligned intro (tagline + subheading + lead paragraph, same pattern as `pourquoi-choisir-acbb.md`'s), 2-3 `.simple_gallery` photo blocks, several `### **heading**` + list detail sections, then the site's standard `.cta-dark` "Pourquoi choisir l'ACBB" CTA and a `mailto:` contact section — the source pages' actual `<form>` (Contact Form 7) was dropped, same as everywhere else on this site with a non-functional WP contact form. The homepage's `.activity-feature` blocks (see below) and `activites.md`'s activity cards both link to these pages internally now. Two of the pages cross-link each other in their body copy (kayak-riviere ↔ kayak-loisir-mer-et-riviere-calme, "vous préférez une pratique plus/moins dynamique...") — keep those internal if either page's slug ever changes.

All 6 have `Status: hidden` — Pelican still generates and serves them normally (`hidden_pages` in `generators.py` is written to output exactly like `pages`), but they're excluded from the `pages` context list, so `base.html`'s main-nav loop and the footer's "Plus de liens" list don't show them as top-level items. Instead, `base.html` renders a `.submenu` dropdown under the "Les activités" `<li>` (desktop: `:hover`/`:focus-within`; mobile ≤1000px: always-expanded inline, since hover isn't reliable there) built from `hidden_pages|sort(attribute='title')`. This assumes `hidden_pages` only ever contains these 6 - if a genuinely separate hidden page is added later, either give it its own handling or this submenu will pick it up too.

## Fidelity philosophy

The theme is a **clean rebuild**, not a pixel-for-pixel clone: keep the real Bridge visual design (colors, typography, grid, buttons) from the original CSS, but drop or replace anything that depended on WordPress plugins, the page-builder editor runtime, or a live backend. When comparing against the live site (`https://www.acbb-canoe-kayak.fr`) for fidelity, match layout/spacing/behavior but don't reintroduce WP-only JS to do it — fix it in `theme.css`/templates instead, the way the existing overrides do.

This extends to markup, not just JS/plugins: templates and content use semantic HTML5 (`<main>`/`<section>`/`<article>`/`<details>`/`<table>`, a `<nav>` for menus and link lists) rather than reproducing WPBakery's div-per-nesting-level page-builder output — that div-grid markup was the *page builder's* implementation detail, not part of the "real Bridge visual design" worth preserving. When adding new layout, reach for the existing `.split`/`.split-narrow`/`.cta-dark`/etc. classes (see "Content is Markdown, presentation is HTML" above) rather than introducing a new wrapper-div convention.

## Instagram/Facebook feeds

The original site's live Instagram feed used a WordPress plugin backed by the Instagram Graph API. There is no anonymous/client-side-only way to reproduce that: Meta retired the old Basic Display API in late 2024, and the current Graph API requires the account to be a Business/Creator account, a registered Meta Developer App, and an OAuth access token that (for Instagram) expires every 60 days and needs a backend to refresh — none of which exists for this project yet. Facebook Page content has the same requirement, though a Page token can be made effectively permanent once obtained.

Given that, the homepage's Instagram grid (raw HTML in `content/pages/accueil.md`, `.instagram_grid`/`.instagram_grid_item` classes) is a **static, self-hosted grid**: real photos from @acbbcanoe downloaded once into `content/images/accueil/instagram/`, each linking out to the real post. It will go stale — there's no automatic refresh. Don't replace it with a third-party embeddable widget (SnapWidget/LightWidget/Elfsight/...) without asking first; that was explicitly declined in favor of self-hosted control. If the club sets up a Meta Developer App + long-lived tokens later, this could become a small scheduled job (e.g. a GitHub Action) that refreshes the cached images/JSON — until then, refreshing it means re-running the same manual fetch (grab current post permalinks + `data-full-res` image URLs from the live site's `#sb_instagram` markup while they're still valid — those CDN URLs are signed and expire after a few days — download them into `content/images/accueil/instagram/`, update the HTML).
